# 함께일하는재단 통합관리시스템 — 서버 전환 설계서

기관 회원 계정 기반의 참여자 포털과 관리자 시스템을 공용 서버에서 운영하기 위한 설계 문서입니다. 현재 단독 HTML 파일에 담긴 개념을 그대로 서버 테이블로 옮기는 것을 전제로 하며, 구현 예시는 **Supabase**(PostgreSQL + 인증 + 파일 저장 + 행 수준 보안)를 기준으로 합니다. Firebase, 자체 서버(Node + PostgreSQL)로도 동일한 구조를 적용할 수 있습니다.

---

## 1. 목표와 역할

이 시스템은 두 종류의 사용자가 하나의 공용 데이터를 공유합니다.

- **참여자(기관 회원)**: 기관마다 이메일·비밀번호로 직접 가입하고 로그인합니다. 자기 기관의 신청서와 결과보고만 보고 작성할 수 있습니다.
- **관리자(재단 매니저)**: 전체 회원·공모사업·신청·정산을 관리합니다.

핵심 원칙은 두 가지입니다. 첫째, 비밀번호는 서버에서 암호화 저장하며 클라이언트에 두지 않습니다. 둘째, "본인 데이터만 보인다"는 규칙은 화면이 아니라 서버(행 수준 보안)가 강제합니다.

## 2. 데이터 모델 (테이블)

### 2.1 profiles (회원 프로필)
Supabase 인증(`auth.users`, 이메일·비밀번호 관리)과 1:1로 연결되는 프로필입니다.

| 컬럼 | 타입 | 설명 |
|---|---|---|
| id | uuid (PK) | `auth.users.id`와 동일 |
| role | text | `participant` / `admin` (기본 participant) |
| kind | text | `org`(기관·기업) / `individual`(개인) |
| name | text | 기관명 또는 성명 |
| org_type | text | 기관 유형 (개인은 비움) |
| affiliation | text | 개인 소속 |
| founded | text | 설립연도 |
| rep | text | 대표자 |
| contact | text | 연락처 |
| sido / sigungu | text | 지역(시도/시군구) |
| approved | boolean | 관리자 승인 여부 (가입 승인제 사용 시) |
| created_at | timestamptz | 가입일시 |

### 2.2 calls (공모사업)
| 컬럼 | 타입 | 설명 |
|---|---|---|
| id | uuid (PK) | |
| title | text | 제목 |
| description | text | 소개 |
| target | text | `org` / `individual` / `both` |
| start_date / end_date | date | 신청 기간 |
| budget | text | 지원 규모 |
| capacity | text | 모집 정원 |
| status | text | `open`(모집중) / `closed`(마감) |
| image_path | text | 대표 이미지 (Storage 경로) |
| created_at | timestamptz | |

### 2.3 applications (신청서 = 관리자 카드)
한 회원이 여러 공모사업에 신청할 수 있으므로 `account_id`와 `call_id`로 묶입니다.

| 컬럼 | 타입 | 설명 |
|---|---|---|
| id | uuid (PK) | |
| account_id | uuid (FK→profiles.id) | 신청한 회원 |
| call_id | uuid (FK→calls.id) | 신청한 공모사업 |
| stage | text | 진행 단계: `applied`/`review`/`in_progress`/`closed`/`aftercare` |
| status | text | 참여자 노출용: `received`/`reviewing`/`selected`/`rejected` |
| motive | text | 신청 동기·욕구 |
| requested_budget | text | 요청 예산 |
| doc_score / interview_score | text | 서류·면접 점수 |
| review_result | text | 선정/미선정/보류 |
| review_opinion | text | 평가위원 의견 |
| mentoring / exec_rate / inspection / issue | text | 사업진행 기록 |
| report_submitted | boolean | 결과보고 제출 여부 |
| performance | text | 핵심 성과 |
| score_accounting … score_linkage | int (0–3) | 5축 진단 점수 |
| classification | text | 분류(성장연계/집중관리/일반/관찰), 수동 지정 시 우선 |
| followup_support / followup_linkage | text | 후속지원·재단 연계 |
| next_contact | date | 다음 접촉 예정일 |
| from_participant | boolean | 참여자 포털에서 접수되었는지 |
| created_at / updated_at | timestamptz | |

### 2.4 result_reports (결과보고)
신청서와 1:1입니다. (단순화하려면 applications 컬럼으로 흡수해도 됩니다.)

| 컬럼 | 타입 | 설명 |
|---|---|---|
| id | uuid (PK) | |
| application_id | uuid (FK, unique) | 대상 신청서 |
| summary | text | 결과 요약 |
| submitted_at | timestamptz | 제출일시 |

### 2.5 settlements / settlement_items (정산)
| settlements | 타입 | 설명 |
|---|---|---|
| id | uuid (PK) | |
| application_id | uuid (FK, unique) | |
| status | text | `none`/`in_progress`/`done` |

| settlement_items | 타입 | 설명 |
|---|---|---|
| id | uuid (PK) | |
| settlement_id | uuid (FK) | |
| name | text | 항목명 |
| planned / spent | numeric | 계획·집행 금액 |
| proof | text | 증빙 메모·링크 |

### 2.6 files (첨부 메타데이터)
실제 파일은 Supabase Storage에 두고, 표에는 메타데이터만 둡니다.

| 컬럼 | 타입 | 설명 |
|---|---|---|
| id | uuid (PK) | |
| owner_account_id | uuid (FK→profiles.id) | 업로더 |
| application_id | uuid (FK, nullable) | 연결 신청서 |
| call_id | uuid (FK, nullable) | 연결 공모사업(이미지) |
| context | text | `application_attachment`/`result_file`/`call_image` |
| storage_path | text | Storage 내 경로 |
| file_name / mime_type / size | text/int | 파일 정보 |
| created_at | timestamptz | |

## 3. 권한 규칙 (Row Level Security)

이 시스템의 보안 핵심입니다. 모든 테이블에 RLS를 켜고, `auth.uid()`(로그인한 사용자 id)를 기준으로 접근을 제한합니다. 관리자 여부는 헬퍼 함수로 판정합니다.

```sql
-- 관리자 판정 함수
create function is_admin() returns boolean language sql stable as $$
  select exists(select 1 from profiles
                where id = auth.uid() and role = 'admin');
$$;
```

정책 요약:

- **profiles**: 본인 행만 조회·수정(`id = auth.uid()`). 관리자는 전체 조회·수정.
- **calls**: 로그인 사용자는 `status='open'` 조회 가능. 등록·수정·삭제는 관리자만.
- **applications**: 참여자는 `account_id = auth.uid()`인 행만 조회·생성·수정(단, 심사 시작 전 단계까지만 수정 허용). 관리자는 전체 권한.
- **result_reports / settlements / settlement_items**: 연결된 신청서의 `account_id = auth.uid()`이면 본인만, 관리자는 전체.
- **files**: `owner_account_id = auth.uid()` 또는 관리자.

예시 정책(신청서 조회):

```sql
alter table applications enable row level security;

create policy "participant reads own apps" on applications
  for select using (account_id = auth.uid() or is_admin());

create policy "participant writes own apps" on applications
  for insert with check (account_id = auth.uid());

create policy "admin manages all apps" on applications
  for all using (is_admin());
```

## 4. 파일 저장 (Supabase Storage)

- 버킷 `attachments`(비공개): 신청 첨부·결과 파일. 경로 규칙 `{account_id}/{application_id}/{파일명}`. 쓰기·읽기는 소유자와 관리자만.
- 버킷 `call-images`(공개 읽기): 공모사업 대표 이미지. 쓰기는 관리자만.
- 업로드 후 `files` 표에 메타데이터를 기록해 어떤 신청·공모에 속한 파일인지 추적합니다.
- 이렇게 하면 단독 파일 버전의 3MB 제한·브라우저 한정 보관 문제가 사라지고, 다른 기기·여러 매니저가 같은 파일을 봅니다.

---

## 5. 인증 흐름

- **회원가입**: 참여자가 이메일·비밀번호로 가입(Supabase Auth) → `profiles` 행 생성(트리거 또는 가입 직후 클라이언트에서). 가입 승인제를 쓰면 `approved=false`로 두고 관리자가 승인.
- **로그인**: Supabase Auth 세션. 로그인 후 `profiles.role`로 참여자/관리자 화면을 분기.
- **비밀번호 재설정**: Supabase 기본 이메일 재설정 사용(자체 서버라면 메일 발송 기능 필요).
- **관리자 계정**: 초기 1~2개를 수동으로 만들고 `role='admin'` 부여.

## 6. 상태값과 화면의 연결

신청서의 `stage`/`status`가 양쪽 화면을 동시에 움직이는 단일 출처입니다.

| 내부 단계(stage) | 참여자 노출(status) | 참여자 화면 표시 |
|---|---|---|
| applied | received | 접수 완료 |
| review | reviewing | 심사 중 |
| review → 결과 | selected / rejected | 선정 / 미선정 |
| in_progress | selected | 사업 수행 중 |
| closed / aftercare | selected | 종료 · 사후관리 |

---

## 7. 화면 흐름

**참여자 포털**
1. 회원가입 / 로그인 / 비밀번호 재설정
2. 내 기관 정보(프로필) 확인·수정
3. 공모사업 목록(모집중) → 신청서 작성·파일 첨부 → 제출
4. 내 신청 내역 + 상태(접수/심사중/선정/미선정)
5. 선정된 사업의 결과보고 작성·파일 업로드·확인

**관리자 콘솔** (현재 시스템 기능 + 추가)
1. 로그인(관리자)
2. 회원(기관) 관리 — 목록·프로필·가입 승인
3. 공모사업 등록·수정·이미지·마감
4. 신청 검토 — 단계·심사·5축 진단·분류
5. 정산 관리
6. 대시보드 — 단계별 현황·검토 대기·지연 후속관리·정산 대기

---

## 8. 현재 데이터 → 테이블 매핑 (이사 가이드)

현재 단독 파일의 한 참여자 카드(JSON)는 다음과 같이 나뉩니다.

- 기관/개인 식별 정보 → `profiles`
- 공모사업 → `calls`
- 신청·심사·진행·종료·진단·분류·사후 필드 → `applications`
- closing/performance, 결과 첨부 → `result_reports` + `files`
- settlement.items → `settlements` + `settlement_items`
- attachments / resultFiles / call.image → Storage + `files`

즉 개념 구조는 그대로이고, 하나의 큰 JSON을 여러 표로 나누고 계정으로 묶는 작업입니다.

---

## 9. 단계별 구축 순서

1. Supabase 프로젝트 생성 → 인증·`profiles`·`calls` 구성. 관리자 로그인과 공모사업 등록부터 이전.
2. `applications` 추가 → 참여자 회원가입·로그인·신청·"내 신청 내역" 연결.
3. `result_reports`·`settlements`·`files`(Storage) 추가 → 결과보고·정산·파일 업로드.
4. RLS 정책 점검·강화, 회원 관리·가입 승인, 대시보드 정비.

각 단계마다 현재 HTML 화면을 거의 그대로 두고 저장 호출만 Supabase로 바꾸면 됩니다.

---

## 10. 보안·운영 주의사항

- 비밀번호는 서버(Supabase Auth)가 해시 저장합니다. 코드·클라이언트에 평문 비밀번호를 두지 않습니다.
- 데이터 격리는 RLS가 보장합니다. 화면에서 숨기는 것만으로는 안전하지 않습니다.
- 개인·기관 정보를 수집하므로 개인정보 수집·이용 동의와 보관기간 정책을 가입 단계에 포함하는 것을 권장합니다.
- 정기 백업은 Supabase가 제공합니다(엑셀 내보내기는 보조 수단으로 유지 가능).
