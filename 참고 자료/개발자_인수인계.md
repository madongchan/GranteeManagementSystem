# 개발자 인수인계 문서 — 함께일하는재단 통합관리시스템

> 프론트엔드(클라이언트) 개발자를 위한 문서입니다. **별도의 서버 개발 없이**, 동작하는 프로토타입을 Supabase(또는 Firebase) 위에 올려 실제 다중 사용자 서비스로 만드는 것을 전제로 합니다.

---

## 0. 한 줄 요약

**동작하는 HTML 프로토타입이 곧 기능 명세서입니다.** 모든 화면·상태·데이터 구조·기능 로직이 여기 들어 있습니다. 할 일은 "저장 위치"를 브라우저(localStorage)에서 **Supabase**로 바꾸고, 로그인을 **Supabase Auth**로 교체하는 것입니다. UI를 새로 설계할 필요는 없습니다.

## 2. 왜 서버 개발이 필요 없나 (Supabase / Firebase)

Supabase는 **PostgreSQL + Auth + Storage + Row Level Security(RLS)**를 클라이언트 JS SDK로 직접 호출하는 BaaS입니다. 프론트에서 `supabase.from('applications').select()` 처럼 부르면 되고, "본인 데이터만 보이게" 하는 보안은 **RLS 정책이 DB 레벨에서 강제**하므로 서버 코드를 따로 쓸 필요가 없습니다. Firebase(Firestore + Auth + Storage + Security Rules)도 동일한 접근이 가능합니다. 설계서는 Supabase 기준으로 작성돼 있습니다.

## 3. 프로토타입에서 재사용 vs 교체

### 그대로 재사용
- 전체 UI / 화면 / 컴포넌트 로직 / 상태 흐름
- 데이터 구조와 필드 정의 (`blankOrg()`, `createApplication()`, 계정 객체 등)
- 기능 로직: 5축 진단·분류(`computeClass`), 정산 집행률·평가(`settleTotalsHtml`, `settlePoor`), 성과지표 달성률, 통계 집계(`viewStats`), 동의 대상자 추출 필터 등

### 교체 지점 (여기만 바꾸면 됨)
현재 프로토타입의 아래 함수들이 **교체 포인트**입니다. 파일에서 함수명으로 검색하면 바로 찾을 수 있습니다.

| 현재 (프로토타입) | 교체 대상 |
|---|---|
| `saveStore()` / `loadStore()` — localStorage에 JSON 통째 저장 | Supabase 테이블 CRUD (`supabase.from(table).upsert/select`) |
| `putFile()` / `getFile()` / `delFile()` — 파일을 base64로 로컬 키 저장 | **Supabase Storage** 업로드/다운로드 (버킷 + 경로) |
| `doLogin()` / `doSignup()` / `logout()` — 계정 배열에서 평문 비교 | **Supabase Auth** (`signUp`, `signInWithPassword`, `signOut`) |
| 참여자 "본인 것만" 필터 (`o.accountId === currentAccountId`) | **RLS로 서버에서 강제.** 클라 필터는 보조 UI용으로만 |
| `exportBackup()` / `importBackup()` | 실서비스에선 선택 (Supabase가 백업 제공). 유지해도 무방 |

### 반드시 바로잡아야 할 것 (프로토타입의 데모용 단축)
- **평문 비밀번호** → Supabase Auth가 해시 저장하도록 대체 (절대 DB에 비밀번호 컬럼 두지 말 것)
- **관리자 크리덴셜 하드코딩**(`ADMIN_ID`/`ADMIN_PW`) → `profiles.role = 'admin'` 기반 판정으로 대체
- **클라이언트 전용 데이터 격리** → RLS 정책으로 대체 (화면에서 숨기는 것만으론 불충분)

---

## 4. 데이터 모델 → 테이블 (요약)

상세 스키마·컬럼·타입·RLS SQL은 **설계서 2·3장**에 있습니다. 개요만:

- `profiles` (회원/역할) ← Supabase `auth.users`와 1:1, `role`(participant/admin), 기관·개인 프로필, 동의(consents), 연령대/규모
- `calls` (공모사업)
- `applications` (신청서 = 프로토타입의 참여자 카드) ← `account_id`, `call_id`, 단계·심사·정산·5축·분류·성과·담당자·동의 스냅샷
- `result_reports` (결과보고, 승인/반려 상태)
- `settlements` / `settlement_items` (정산 + 정산평가)
- `files` (첨부 메타데이터, 실제 파일은 Storage)

프로토타입의 한 참여자 카드(JSON 하나)가 위 여러 테이블로 나뉩니다. 매핑은 설계서 8장에 정리돼 있습니다.

---

## 5. 권장 구현 순서 (프론트 관점)

1. Supabase 프로젝트 생성 → 설계서의 테이블 생성 + **RLS 정책 적용**(설계서 3장 SQL 복붙)
2. Supabase Auth 연결 → `doLogin`/`doSignup`/`logout` 교체, `profiles` 생성 트리거
3. 저장 계층 교체 → `saveStore`/`loadStore`를 테이블 CRUD로 (화면별로 필요한 쿼리만 부르도록 분리 권장)
4. Storage 연결 → `putFile`/`getFile`/`delFile` 교체, 첨부·공모 이미지 버킷 (비공개/공개)
5. 통계·백업 등 부가 기능 정리, RLS 최종 점검

**프레임워크 선택(선택 사항):** 지금은 프레임워크 없는 단일 HTML입니다. 그대로 Supabase만 붙여도 동작하지만, 유지보수를 생각하면 **React/Vue 등으로 이관**하는 것을 권장합니다. 화면·로직이 이미 확정돼 있어 이관이 어렵지 않습니다.

## 6. 참고

- 스택 대안: **Supabase**(추천, 설계서 기준) 또는 **Firebase**. 소규모 비영리에 적합하며 무료 구간이 있습니다.
- 개인정보 동의는 화면·흐름은 구현돼 있으나, **동의 이력 보관·철회·보관기간**은 실서비스에서 정식으로 갖춰야 합니다(개인정보처리방침 연결 포함).
- 현재 프로토타입은 데이터가 브라우저에 저장되어 여러 사용자가 동시에 공유할 수 없습니다. 이 한계를 없애는 것이 이번 작업의 목적입니다.
