## 1. 결정 사항

| 항목 | 결정 | 근거 |
|---|---|---|
| 프레임워크 | **Next.js (App Router) + TypeScript** | 프로토타입 최대 결함이 "폼 상태가 DOM에만 존재"라 저장소만 교체해선 해소 불가. 서버 컴포넌트로 관리자 조회 부담 분리 |

## 2. 계승할 도메인 로직 (그대로 옮김)

프로토타입에서 실무 가치가 있는 부분. 전부 **순수 함수**라 TypeScript로 1:1 이관 가능하다.

### 2.1 5축 진단 → 4분류

```ts
// 5축, 각 0(미입력)~3(우수). 1=미흡 2=보통 3=우수
type Axis = 'accounting' | 'execution' | 'outcome' | 'sustainability' | 'linkage'

안정성(stability) = accounting + sustainability      // 0~6, 임계 >= 5
잠재력(potential) = execution + outcome + linkage    // 0~9, 임계 >= 7

              잠재력 높음        잠재력 낮음
안정성 높음    성장연계          일반 모니터링
안정성 낮음    집중관리          관찰
```
- 5축 중 하나라도 0이면 **미분류**.
- `followup.manual`(수동 지정)이 있으면 자동 분류보다 **우선**한다 (`effectiveClass`).
- 분류별 대응 지침 문구(`classExplain`)도 그대로 계승.

### 2.2 5단계 흐름과 참여자 노출 상태

내부 단계(관리자)와 참여자에게 보이는 상태를 분리한다. 이것이 양쪽 화면을 움직이는 단일 출처.

| 내부 stage | 참여자 status | 참여자 화면 |
|---|---|---|
| `applied` | `received` | 접수 완료 |
| `review` | `reviewing` | 심사 중 |
| `review`(결과 확정) | `selected` / `rejected` | 선정 / 미선정 |
| `in_progress` | `selected` | 사업 수행 중 |
| `closed` | `selected` | 종료 |
| `aftercare` | `selected` | 사후관리 |

> 프로토타입은 stage를 배열 인덱스 정수(0~4)로 저장. **텍스트 enum으로 변환**한다 (순서 변경 시 기존 데이터가 깨지는 것을 방지).

### 2.3 정산

- 항목별 `planned` / `spent` / `proof` → 총계와 집행률 자동 산출.
- 3축 정산평가: 일정 준수 / 충실도 / 소통 원활성. 각 3단계.
- **하나라도 최하 등급이면 "정산 부실"로 플래그** (`settlePoor`) → 대시보드 노출.

### 2.4 그 외
- 성과지표(KPI): 지표명·목표·실적 → 달성률
- 활동 이력(방문/연락/기타 + 일자 + 메모)
- 결과보고 승인/반려(반려 사유 필수)
- 동의 항목별 대상자 추출 필터(후속지원·조사참여·연구활용)
- 통계: 분류별·유형별·지역별·동의별 집계
- 엑셀 내보내기/가져오기

## 4. 데이터 모델 (설계서 대비 변경점)

기본 골격은 제공된 설계서 2장을 따르되 아래를 **추가·수정**한다.

### 4.1 추가 테이블
- **`audit_logs`** — `id`, `actor_id`, `table_name`, `record_id`, `field`, `old_value`, `new_value`, `created_at`
- **`kpis`** — `id`, `application_id`, `name`, `target numeric`, `actual numeric` (프로토타입 `o.kpis`)
- **`activities`** — `id`, `application_id`, `date`, `type`(방문/연락/기타), `note` (프로토타입 `o.activities`)

> 설계서에는 KPI·활동이력 테이블이 누락되어 있다. 프로토타입에는 구현돼 있으므로 반드시 추가.

### 4.2 `applications` 수정
- `stage` : 정수 → `text` enum (`applied`/`review`/`in_progress`/`closed`/`aftercare`)
- `requested_budget`, `doc_score`, `interview_score`, `exec_rate` : `text` → `numeric`/`int`
- `applicant_snapshot jsonb` **추가** (결함 #7)
- `display_no text unique` **추가** (결함 #5)
- `report_status text` + `report_reject_reason text` **추가** — 설계서 누락. 프로토타입에 승인/반려 기능 존재
- `classification`은 저장하지 않고 **생성 열 또는 뷰**로 산출. 단 `classification_manual`은 별도 컬럼으로 저장

### 4.3 `settlements` 수정
- 3축 정산평가 컬럼 추가: `eval_schedule`, `eval_faithfulness`, `eval_communication`, `eval_note` — 설계서 누락, 프로토타입에 존재

### 4.4 `profiles` 유지 + 확인
- `approved boolean` 승인제 실제 사용 여부 → **운영 정책 확인 필요** (미결 #1)
- `consents jsonb` — 동의 5종(수집·제3자·연구활용·후속지원안내·조사참여) + `agreed_at` + `version`

## 5. 권한 (RLS)

설계서 3장 정책을 채택하되 다음을 보강한다.

- `is_admin()` 헬퍼는 `security definer`로 두고 `profiles` 재귀 참조 무한루프를 피한다.
- `applications` 참여자 수정 권한은 **`stage='applied'`일 때만** 허용 (심사 시작 후 잠금).
- `audit_logs`는 참여자에게 **select 불허**, 관리자만 조회.
- `kpis`/`activities`/`settlements`는 참여자 **읽기만**, 쓰기는 관리자.
- Storage 정책도 테이블 RLS와 별개로 버킷 정책을 반드시 설정 (누락 시 URL 아는 사람 전원 접근).

# 개정 1차 — 인프라·인증 구조 확정 (2026-07-28)

사용자 요구사항 추가 반영. 위 본문의 1장·5장·8장을 다음으로 **갱신**한다.

## A. 인프라 확정

| 항목 | 결정 | 비용 |
|---|---|---|
| DB·인증·파일 | **Supabase** | 무료 시작 (DB 500MB / 파일 1GB) → 필요 시 Pro $25/월 |
| 배포 | **Vercel** | 무료 시작 → 기관 운영은 Pro $20/월 권장 |
| 도메인 | 미구매. 개발은 `*.vercel.app`으로 진행 | 약 2만원/년 |

전용 서버·직접 DB 운영은 배제. 사용자가 유니티 클라이언트 개발자로 백엔드 상시 운영 인력이 없어, 보안 패치·백업이 방치될 위험이 크기 때문.

## B. DB 분리 요구에 대한 결론

사용자 요구는 "참여자 페이지와 관리자 페이지를 나누고 DB도 구분". 이 중 **DB 물리 분리는 채택하지 않는다.**

- 관리자가 다루는 신청서 = 참여자가 제출한 바로 그 레코드. DB를 나누면 실시간 동기화 계층이 필요하고, 불일치 시 "관리자는 선정 처리했는데 참여자 화면은 심사중" 같은 버그가 발생한다.
- 요구의 실질(관리자 화면 접근 차단, 참여자 간 데이터 격리)은 **단일 DB + RLS**로 완전히 달성되며, 코드가 아닌 DB 엔진이 강제하므로 오히려 더 안전하다.
- 사용자 승인 완료 (2026-07-28).

## C. 사이트 분리 방식

**Next.js 프로젝트 1개 + 미들웨어 호스트명 분기.**

```
admin.도메인 → /admin/*  로만 진입. 참여자 화면 미노출
www.도메인   → 참여자 화면만. /admin 접근 시 404
```

모노레포 2앱 분리는 배포 설정·환경변수·공용 도메인 로직을 이중 관리해야 해 **1인 유지보수 환경에 부적합**하다고 판단해 배제. Next.js App Router가 화면 단위로 번들을 분할하므로 참여자 브라우저에 관리자 코드가 내려가지 않으며, 실제 방어선은 주소 은닉이 아닌 서버측 `role='admin'` 검증이다.

## D. 인증 구조

계정 저장소는 Supabase Auth 하나, 로그인 창구만 둘로 나눈다.

| | 참여자 | 관리자 |
|---|---|---|
| 방식 | 구글 / 카카오 OAuth | 이메일 + 비밀번호 |
| 가입 | 소셜 로그인 시 자동 생성 | **화면에 가입 기능 없음.** Supabase 대시보드에서 수동 생성 후 `role='admin'` 부여 |
| 검증 | — | 로그인 성공 + `role='admin'` **이중 확인** |

- `handle_new_user` 트리거로 신규 계정에 `profiles` 행 자동 생성. 이때 role은 **항상 participant**.
- `guard_profile_role` 트리거로 참여자의 자기 권한 승격을 차단 (RLS만으로는 특정 컬럼 변경을 막을 수 없음).
- ⚠️ **카카오 로그인 선결과제**: 카카오 개발자센터 앱 등록 + 이메일 수집을 위한 **비즈니스 앱 전환(사업자등록번호 필요)**. 재단 명의 서류 확보 필요. 구글은 제약 없음.

## E. 도메인 권고

1. `.or.kr` — 비영리단체 전용, 신뢰도 최상. **법인 서류 필요**
2. `.kr` / `.co.kr` — 서류 불필요, 즉시 구매

## F. 산출물

- `supabase/migrations/0001_init.sql` — 테이블·enum·트리거·RLS·Storage 버킷 정책 전체
- ⚠️ **아직 실제 Supabase 프로젝트에서 실행·검증하지 않음.** 프로젝트 생성 후 적용하며 오류를 잡아야 함.

### 스키마 작성 중 발견해 반영한 사항
- `settlements.is_poor` — 미평가(null)가 부실로 오분류되지 않도록 `coalesce` 처리
- 감사 트리거 — 동적 SQL `($1).필드명` 방식은 파라미터 타입 미확정으로 실패. `to_jsonb` 비교로 변경
- `calls` 조회 정책 — 모집중만 허용하면 **마감 후 "내 신청 내역"에서 사업명이 사라짐**. 본인이 신청한 공모는 마감 후에도 조회 가능하도록 조건 추가
- Storage 정책의 `is_admin()`은 `public.` 스키마 한정 필요
